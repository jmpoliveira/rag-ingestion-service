# ADR 0005: Retrieval evals over a public sample corpus, published to Phoenix

Status: accepted

## Context

Ingestion decisions (chunk size and overlap, cleaning, the embedding model, task prefixes,
the distance) are only good or bad through their effect on retrieval: does the right passage
come back for a question? Unit tests cannot answer that; they prove the machinery. The
agent's evals (ai-agent-service ADR 0005) measure tool use; nothing measured the index.

The old service was tested on four private PDFs, which cannot go into a public repository.

## Decision

1. **A public, fictional sample corpus** in `samples/knowledge-base`: help-centre articles of
   an invented product (Tessera Support Cloud) whose customers are the mcp-server's mock
   customers, in Markdown, plain text and a subfolder. `make ingest-samples` puts it in its own
   collection (`EVAL_COLLECTION`, default `tessera-kb`), never the real one.
2. **A small in-repo harness** (`evals/`), mirroring the agent's: TOML dataset validated by
   pydantic (unknown fields rejected), deterministic graders, a JSON report as the source of
   truth, a baseline comparison with a warning when the dataset differs, and the git commit
   and fingerprints in every report.
3. **Metrics** per case, with k fixed by the dataset: hit@k, reciprocal rank (MRR overall),
   recall@k (for questions that need several documents), and **evidence** (a relevant chunk in
   the top k contains the answer text; a hit on the right document with the wrong chunk is a
   chunking problem, not an embedding problem). Results per tag: plans, SLA, paraphrase,
   multi-document, Portuguese...
4. **The eval uses the service's own components** (`build_embedder`, `build_index_provider`
   from `main.py`), so the embedder under test is the one that wrote the index. It refuses to
   run when the dataset's documents are not in the collection.
5. **One run per case.** Embeddings and search are deterministic for a fixed model and index,
   unlike the agent's model runs, which need repeats.
6. **Published to Phoenix**, as in the agent (its ADR 0006): a `ResultSink` port and a Phoenix
   adapter, the only module that imports `phoenix`, from the optional `.[evals]` extra. Dataset
   `<name>-v<version>-<fingerprint>`; one experiment per report; one run per case with the
   ranked hits; evaluations for each metric. Each case is its own trace (query embedding,
   then search), linked from its Phoenix run.

## Alternatives considered

- **RAGAS / DeepEval / Phoenix's own retrieval evals.** Strong on answer-level metrics with an
  LLM judge (faithfulness, context precision). Retrieval at this level needs no judge, and the
  agent already showed that a small harness keeps every mechanism visible. Answer-level evals
  belong where answers are generated: the agent, once `search_knowledge_base` exists.
- **Synthetic questions generated by an LLM from the chunks.** Scales the dataset, but the
  questions inherit the chunk's wording, which flatters lexical overlap. A good next step,
  with the hand-written cases kept as the trusted core.
- **Evaluating on the private PDFs.** Realistic, but not reproducible by anyone else; keep
  such a dataset outside the repository if needed.

## Consequences

- `make eval` needs Ollama and Chroma running; it is not part of `make check` or CI.
- The first baseline (default settings, no prefixes) is still to be run in the real
  environment; the harness was verified end to end against a real Chroma with a toy
  embedder only.
- Changing a sample document means reviewing the cases and bumping the dataset version; a
  test checks that every expected source exists and every evidence text appears in it.
